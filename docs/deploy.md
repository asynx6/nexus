# Deploying a NEXUS project

A NEXUS project (`nexus init`) is a Node ≥22 process plus a directory for the
event store. It runs the same binary locally and in the cloud — there is no
separate server build.

## What a deploy needs

1. **Node ≥ 22** (for `node:sqlite` and the built-in test runner).
2. **A persistent volume** at `.nexus/store` — this is the event log. Losing it
   means losing every run's history; it is not regenerable.
3. **The gateway env** — either `.env-gateway` in the image or the env vars
   `NEXUS_GATEWAY_BASE` / `NEXUS_GATEWAY_KEY` / `NEXUS_GATEWAY_MODELS`.
   Secrets belong in the platform secret store, never in the image.
4. **A port** only if you run `nexus replay --port` (the dashboard). A pure
   `nexus run` worker needs no inbound port at all.

## Dockerfile (generated by `nexus init`)

```dockerfile
FROM node:22-slim
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm ci --omit=dev
COPY . .
RUN mkdir -p .nexus/store
# nexus replay dashboard (optional); drop this if it is a run-only worker
EXPOSE 9090
CMD ["npx", "nexus", "replay", "--port", "9090", "--host", "0.0.0.0"]
```

Build and run locally first — this catches the two common failures before you
pay for a cloud instance:

```bash
docker build -t nexus-app .
docker run -p 9090:9090 -v "$PWD/.nexus/store:/app/.nexus/store" \
  -e NEXUS_GATEWAY_BASE=$NEXUS_GATEWAY_BASE \
  -e NEXUS_GATEWAY_KEY=$NEXUS_GATEWAY_KEY \
  nexus-app
```

If the volume is omitted the container still runs, but every restart starts a
fresh event log — the events are written inside the container and die with it.

## One-command deploys

### Fly.io

```bash
fly launch --no-deploy          # writes fly.toml from the Dockerfile
fly volumes create nexus_store  # the persistent event store
fly secrets set NEXUS_GATEWAY_BASE=... NEXUS_GATEWAY_KEY=...
fly deploy
```

`fly.toml` must mount the volume so the event log survives restarts:

```toml
[mounts]
  source = "nexus_store"
  destination = "/app/.nexus/store"
```

### Railway

```bash
railway up                       # builds the Dockerfile
railway variables set NEXUS_GATEWAY_BASE=... NEXUS_GATEWAY_KEY=...
```

Add a persistent volume in the Railway dashboard at `/app/.nexus/store`.

### Render

```bash
render deploy                     # uses the Dockerfile
```

Create a **Disk** mounted at `/app/.nexus/store` in the service settings, then
set the gateway env vars under Environment.

### Plain VPS

```bash
git clone <repo> && npm ci --omit=dev
pm2 start "npx nexus replay --port 9090 --host 0.0.0.0" --name nexus
pm2 save                          # auto-restart on reboot
```

Point nginx at `:9090` for TLS. Back up `.nexus/store` — it is the only state.

## Checklist before the first deploy

- [ ] `nexus doctor` passes locally against the same gateway env.
- [ ] `.nexus/store` is on a persistent volume (not the container filesystem).
- [ ] `NEXUS_GATEWAY_KEY` is in the platform secret store, not the image.
- [ ] Docker builds and the healthcheck returns 200 after boot.
- [ ] One successful `nexus run` against the deployed instance.

## Health check

`nexus healthz` exits 0 when the gateway is reachable and returns structured
JSON, so it works as a readiness probe:

```bash
nexus healthz || exit 1
```

For a container probe, wrap it in an ENTRYPOINT script or call the JSON
endpoint directly — `GET <base>/models` is the underlying check.
